Le VPN (Headscale / Tailscale)

Le VPN maille les zones, le serveur de coordination et les appareils distants : Headscale 🡕 coordonne depuis le HCS, Tailscale 🡕 est le client de chaque nœud. Cette page réunit les gestes d’exploitation. Routage, DNS, MagicDNS, politique d’accès et clés sont expliqués dans Fonctionnement du tailnet.

Activer le VPN

Section intitulée « Activer le VPN »

Activer la coordination et déclarer le HCS (profile: hcs) suffit :

Le rôle de chaque nœud se déduit de la topologie :

NœudIdentitéRôle
HCStag:hcscoordination, DNS pivot, services globaux, exit node (fermé)
Passerelletag:gw-<zone>routeur de sous-réseau : publie le /16 de sa zone
Poste d’administrationtag:adminSSH vers toutes les machines
Appareil personnelson propriétaireservices, selon ses groupes

Un poste d’administration est un hôte dont groups contient admin et dont le fichier d’hôte active le client :

autoPauseOnLan met le client en pause quand le portable est branché dans une zone (NetworkManager requis).

Enrôler une machine

Section intitulée « Enrôler une machine »

Les machines rejoignent le tailnet sans clé partagée : le HCS crée pour chacune une clé à usage unique, avec ses tags déclarés. just configure s’en charge, donc just full-install aussi. La recette seule se relance à tout moment :

Elle est idempotente :

SituationEffet
Nœud enrôlé, nom et tags conformesrien (already enrolled)
Tags ou nom différentscorrigés sur le HCS, sans reconnexion
Jamais enrôlé, supprimé ou réinstallénouvelle clé, enregistrement
Ancien nœud du même nom hors lignesupprimé, le nouveau prend le nom
Ancien nœud du même nom en lignerefus : deux machines portent ce nom
Hôte sans client Tailscaleignoré

Le mécanisme est détaillé dans Clés d’activation et enrôlement.

Déployer le HCS après avoir déclaré l’hôte

Le HCS ne crée une clé que pour un hôte qu’il connaît. Un hôte tout juste ajouté à etc/config.yaml exige d’abord just apply hcs, sinon : no declared tailnet identity.

Échec pendant une installation

HCS injoignable, just configure avertit sans s’arrêter : relancer just tailnet-enroll <hôte> une fois le HCS revenu.

Nouvelle adresse après une réinstallation

Headscale attribue les adresses dans l’ordre et ne permet pas de les fixer. Une machine réinstallée reçoit une nouvelle adresse tailnet : pour une passerelle, la reporter dans vpn.ipv4. Pour la conserver, restaurer l’état du client plutôt que ré-enrôler (voir Migrer le matériel d’une passerelle).

Connecter un appareil personnel

Section intitulée « Connecter un appareil personnel »

Un smartphone ou un ordinateur personnel se connecte avec l’identité Kanidm de son propriétaire : ni clé, ni validation manuelle.

Peut se connecterCondition dans etc/config.yaml
Administrateurprofil admin ou nix-admin
Membre d’une zonegroupe zone-<zone>

Ces comptes forment le groupe Kanidm tailnet, provisionné tout seul ; Kanidm refuse les autres. Pour ouvrir l’accès, ajouter le groupe à l’utilisateur, régénérer, puis just apply hcs. L’utilisateur suit ensuite Connecter un appareil.

L’appareil appartient à la personne (alice@) et expire après 180 jours : elle se reconnecte alors avec son identifiant.

Page de connexion introuvable

Le DNS scindé envoie tout domain.tld au HCS par le tunnel, y compris headscale.domain.tld et idm.domain.tld. Tant que le tunnel n’est pas monté, le navigateur ne les résout pas. Contournement : désactiver « Use Tailscale DNS » dans l’application le temps de la connexion, puis le réactiver.

Adapter la politique d’accès

Section intitulée « Adapter la politique d’accès »

La politique est générée depuis la topologie : ses règles sont détaillées dans Politique d’accès. Des options l’ajustent, sur le HCS :

Option darkone.service.headscale.DéfautEffet
policy.adminDevices{ }appareils personnels autorisés en SSH : nom → IPv4 tailnet
policy.exitNodeSources[ ]sources autorisées à sortir sur Internet par le HCS
policy.extraHosts{ }alias supplémentaires : nom → CIDR
policy.extraAcls[ ]règles ajoutées après les règles générées
policy.enforcetruefalse : tout autorisé, pour une migration seulement
nodeExpiry"180d"expiration des appareils personnels (0 : jamais)

Puis just apply hcs : la politique est vérifiée à la construction, et Headscale la recharge sans redémarrer.

Adresse d’un appareil déclaré

adminDevices vise une adresse IPv4. Un appareil réenregistré comme nouveau nœud change d’adresse : HeadscaleNodeDrift le signale, reporter la nouvelle.

Exit node

Ouvrir exitNodeSources ne suffit pas : l’utilisateur choisit le HCS comme exit node dans son application.

Administration

Section intitulée « Administration »

Sur le HCS (just enter hcs) :

CommandeUsage
sudo headscale nodes listnœuds, propriétaire, tags, adresses, expiration
sudo headscale nodes list-routesroutes annoncées et approuvées
sudo headscale nodes rename -i <id> <nom>renommer un nœud
sudo headscale nodes expire -i <id>forcer une reconnexion
sudo headscale nodes delete -i <id>supprimer un nœud
sudo headscale users listpropriétaires d’appareils personnels
sudo headscale preauthkeys listclés pré-autorisées : tags, usage, expiration
sudo headscale policy getpolitique servie
sudo dnf-tailnet-enroll status <hôte>identité déclarée d’un hôte

Tags et routes ne se règlent pas à la main : just tailnet-enroll pose les tags déclarés, la politique approuve les routes. Les autres réglages du client (routes annoncées, SSH Tailscale coupé, exit node) sont réalignés par tailscaled-autoconnect, au démarrage et aux déploiements qui le modifient.

Sorties JSON

nodes list -o json et preauthkeys list -o json peuvent contenir des clés pré-autorisées : ne pas les copier dans un ticket ou un salon.

Audit et alertes

Section intitulée « Audit et alertes »

Toutes les 15 minutes, headscale-audit compare les nœuds réels à la topologie déclarée, sans rien modifier. Le détail des écarts est dans son journal :

AlerteSignaleAprès
HeadscaleNodeDriftHCS ou passerelle absent, tags faux, adresse différente de celle déclarée30 min
HeadscaleUnexpectedNodenœud tagué non déclaré, ou appareil d’un compte hors du groupe tailnetaussitôt
HeadscalePolicyInvalidpolitique refusée, ou politique servie différente du fichier30 min
HeadscaleOidcFallbackKanidm absent au démarrage de Headscale : connexions OIDC coupéesaussitôt
HeadscaleNodeExpiringappareil personnel qui expire sous 7 jours1 h
HeadscaleAuditStaleaudit sans succès depuis plus d’une heureaussitôt

Toutes sont en warning, sur le Prometheus qui supervise le HCS. Un poste d’administration absent n’est pas une anomalie ; présent, ses tags sont vérifiés.

Après HeadscaleOidcFallback

Kanidm revenu, relancer Headscale : sudo systemctl restart headscale.

Auto-réparation du client

Section intitulée « Auto-réparation du client »

Un tailscaled peut décrocher silencieusement de Headscale : la connexion de contrôle est perdue alors que le service reste « actif », et le sous-réseau d’une passerelle devient injoignable. Un watchdog local détecte et corrige ce cas, sur chaque client Tailscale.

AspectComportement
Sondetoutes les 60 s : tailscale status (backend, état en ligne)
Anti-rebond3 sondes en échec d’affilée (~3 min) avant d’agir
Correctionredémarre tailscaled, qui se reconnecte au plan de contrôle
Anti-boucleune seule correction par fenêtre de 10 min
Nœud non enrôléaucun redémarrage (NeedsLogin) : just tailnet-enroll
Portable en pausewatchdog à l’arrêt, métrique retirée
Observabilitédnf_tailscale_healthy, dnf_tailscale_selfheal_restarts_total (textfile node_exporter)

Deux alertes accompagnent le mécanisme :

  • TailscaleUnhealthy : toujours décroché après 10 min, malgré la correction ;
  • TailscaleFlapping : plus de 3 corrections en une heure.

Activé par défaut

Pour le désactiver sur un hôte : darkone.service.tailscale.selfHeal.enable = false;.

Amorçage du plan de contrôle

Section intitulée « Amorçage du plan de contrôle »

Sur une passerelle, dnsmasq envoie tout domain.tld au résolveur du HCS à travers le tailnet : le client aurait besoin du VPN pour trouver le serveur qui monte le VPN. Au démarrage, en plus, le résolveur local n’écoute pas encore.

Chaque client Tailscale reçoit donc l’adresse publique du HCS dans son /etc/hosts, déduite de etc/config.yaml (le HCS lui-même est exclu). dnsmasq répond à ce nom depuis ce fichier, sans jamais le transmettre :

Le client se connecte ainsi sans aucun résolveur, y compris quand le DNS local est en panne, précisément quand l’auto-réparation doit pouvoir agir.

Changement d’adresse du HCS

/etc/hosts prime sur le DNS. Si le VPS change d’adresse, mettre à jour etc/config.yaml puis redéployer les clients Tailscale : tant qu’ils portent l’ancienne entrée, ils ne se reconnectent pas, même avec un DNS public correct.

Hors d’une zone

Section intitulée « Hors d’une zone »
  • Appareil personnel : voir Connecter un appareil personnel.
  • Portable d’administration : en déplacement, il joint toutes les zones par le tailnet (just enter <hôte>). Rebranché dans une zone, son client se met en pause et la passerelle locale reprend la main.
