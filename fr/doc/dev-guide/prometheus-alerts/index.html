Les alertes Prometheus

Carte de maintenance du code d’alerte : où se trouve quoi, et comment l’étendre sans rien casser. Le fonctionnement côté administrateur est décrit dans Monitoring & Alertes.

Logique pure vs câblage

Section intitulée « Logique pure vs câblage »

Le code est scindé en deux, pour garder la génération des règles testable :

  • dnf/lib/alerts.nix : fonctions pures qui produisent les règles Prometheus à partir de la topologie. Testées dans dnf/tests/unit/lib/alerts_test.nix.
  • dnf/modules/service/prometheus.nix : câblage impur (Alertmanager, routage par sévérité, sops, bot Matrix, vhost, sondes blackbox).

Toute logique non triviale va dans alerts.nix ; le module se contente de la brancher.

Le label host, ou pourquoi les alertes se nomment

Section intitulée « Le label host, ou pourquoi les alertes se nomment »

Chaque cible de scrape porte un label host valant le nom d’hôte, posé par mkHostTargets dans prometheus.nix (un static_config par hôte plutôt qu’une liste unique de cibles). Deux effets :

  • le bot Matrix affiche DiskSpaceLow at srv-backup au lieu de l’instance brute <ip>:<port> ;
  • une route de silence peut viser une seule machine.

Le poser au scrape le propage gratuitement à toutes les alertes issues de ces jobs, y compris les règles ressources génériques, qui ignorent tout de la topologie à l’évaluation.

Les sondes blackbox n’ont pas de host (la cible est une IP). PeerGatewayDown le pose donc dans la règle, avec le nom de la passerelle visée. Sans lui, les règles d’une zone ne différeraient que par leur expr → promtool les signale comme doublons.

Les agrégations effacent les labels

Une clause by (...) supprime tout label non groupé. ResticBackupStale (max by (instance, backup, host)), SynapseHighErrorRate (sum by (instance, host)) et les règles FS (byDevice) citent donc host explicitement. L’oublier dans une nouvelle règle agrégée fait retomber la notification sur l’instance brute.

Un label job exporté est renommé au scrape

Le job de scrape pose son propre label job. Celui d’une métrique exportée (collecteur textfile compris) devient donc exported_job. La métrique restic porte le nom du job dans backup : grouper sur job fusionnerait tous les jobs d’un hôte, et un job en échec resterait masqué tant qu’un autre réussit.

Un job jamais réussi n’a pas de série

dnf_restic_last_success_timestamp n’existe qu’après un premier succès. Le module restic exporte donc aussi dnf_restic_declared_timestamp, date de première déclaration de chaque job. Les règles prennent le succès, or la déclaration à défaut : deux agrégats by (instance, backup, host), le côté gauche l’emporte. Sans cette liste, un nœud garde l’ancien comportement.

Règles FS : une alerte par partition

node_filesystem_* est émis par montage. Une partition montée plusieurs fois (sous-volumes btrfs, montages bind) déclenchait donc chaque règle FS autant de fois qu’elle a de montages, pour un seul disque plein.

mkResourceRuleGroups agrège sur byDevice (instance, job, host, device, fstype) : min pour l’espace et les inodes, max pour FilesystemReadOnly. Les deux membres du and de DiskWillFillSoon sont agrégés — un membre brut porte encore mountpoint et ne matche plus rien en face.

mountpoint disparaît avec l’agrégation. PromQL ne sait pas concaténer des valeurs de label : la liste des montages est donc résolue par la fonction query du moteur de templates Go que Prometheus applique aux annotations (deviceMounts). Coût : une requête instantanée par alerte active et par évaluation, aucune tant que la règle reste muette.

Le bot n’affiche pas summary

Le bot Matrix rend le titre puis l’annotation description, et ne se rabat sur summary que si description est absente : toutes les règles DNF en définissent une, donc summary ne lui parvient jamais. Une information à faire figurer dans la notification doit aller dans description.

Sélection des nœuds surveillés

Section intitulée « Sélection des nœuds surveillés »

La supervision est opt-out pour l’infrastructure, opt-in pour le reste. nodeAlertEligible retient un nœud uniquement s’il est de classe critical (profil gateway/hcs/server ou feature alert-critical), s’il porte explicitement alert-non-critical, ou s’il héberge au moins un service mappé dans serviceUnits. Un laptop/desktop nu ne génère donc aucune alerte node.

Panne internet vs hôte distant down

Section intitulée « Panne internet vs hôte distant down »

Le Prometheus d’une zone joint les hôtes des autres zones (ex. le HCS public) uniquement via le WAN. Quand internet tombe, ces cibles deviennent injoignables et déclencheraient un faux « host down ». Pour l’éviter :

  • chaque règle node porte un label reach (local même zone, wan cross-zone) ;
  • une sonde blackbox ICMP vers des IP externes alimente ZoneInternetDown (déclenchée seulement si toutes les cibles externes échouent) ;
  • une règle d’inhibition Alertmanager (equal: [zone]) fait taire les alertes reach="wan" de la zone tant que ZoneInternetDown est active — la vraie cause est notifiée, pas les symptômes.

Le piège : un seul document de règles

Section intitulée « Le piège : un seul document de règles »

À ne jamais oublier

NixOS concatène toutes les entrées de services.prometheus.rules (une liste de chaînes) dans un seul fichier. Plusieurs documents groups: sans séparateur --- → seul le premier est lu. Empiler une deuxième entrée casse silencieusement les groupes suivants.

On fusionne donc tout via mergeRuleGroups, puis on n’émet qu’une entrée :

Exclure plutôt que taire

Une condition permanente et voulue ne se met pas sous silence : alerting.silences coupe la notification mais laisse l’alerte se déclencher, donc rougir les UI, pour toujours. Elle doit sortir du sélecteur de la règle. Deux listes de seuils le font, dans mkResourceRuleGroups :

  • remoteFstypes — retiré de toutes les règles FS. Un montage client remonte l’espace du serveur : le surveiller transforme un export plein en une même alerte sur chaque machine qui le monte, alors que le serveur alerte déjà tout seul, avec la vraie partition.
  • readOnlyByDesignFstypes — retiré de FilesystemReadOnly seul (médias optiques). La règle ne surveille donc que les montages censés être accessibles en écriture.

Convention DNF

Un helper de lib/ = un test. Toute fonction ajoutée à alerts.nix se double d’un cas dans dnf/tests/unit/lib/alerts_test.nix (nix-unit).

Ordre des routes Alertmanager

continue vaut false par défaut : la première route enfant qui matche gagne. Les routes de mkSilenceRoutes doivent donc être insérées avant les routes par sévérité, sinon elles ne sont jamais atteintes et l’alerte notifie quand même. Le receiver null est partagé avec la route de maintenance, d’où sa garde silenceOnRebuild || silences != [] : référencer un receiver absent empêche Alertmanager de démarrer.

Métrique textfile : permissions

Un fichier .prom du collecteur textfile doit être lisible par node-exporter (utilisateur non-root). mktemp crée en 0600 : poser un chmod 0644 avant le mv atomique, sinon le fichier est ignoré (node_textfile_scrape_error 1) et la métrique n’est jamais exposée, donc l’alerte reste aveugle.
