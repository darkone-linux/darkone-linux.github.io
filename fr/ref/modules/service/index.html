✨ darkone.service.dnsmasq

Section intitulée « ✨ darkone.service.dnsmasq »

dnsmasq pré-configuré pour la passerelle / routeur local.

Note

Cette configuration lit la conf network dans le fichier config.yaml. C’est la fonctionnalité essentielle de la passerelle locale.

Hôtes venant d’une autre zone

Chaque zone réserve <ipPrefix>.6.0/24 pour les hôtes dont le domicile est ailleurs. Le générateur émet, dans zone.extraDnsmasqSettings, un dhcp-host par MAC de flotte connu non natif ici, plus un host-record liant <host>.<this-zone-domain> à cette adresse, de sorte qu’une machine branchée sur la mauvaise zone (installation d’une passerelle, ordinateur portable en itinérance) obtienne quand même un bail et un nom prévisibles. Son nom court continue de résoudre vers son adresse de domicile. zone.roaming expose la même table à l’outillage d’installation.

  • enable bool Active le service dnsmasq local

✨ darkone.service.garage

Section intitulée « ✨ darkone.service.garage »

Un service Garage S3 local entièrement configuré.

Fournit un stockage d’objets interne compatible S3 accessible uniquement sur 127.0.0.1:3900.

Création manuelle des buckets

Les buckets ne sont PAS créés automatiquement par ce module. Chaque service consommateur provisionne son propre bucket et sa clé d’accès via une unité systemd oneshot dédiée ordonnée After= garage-init.service. Les identifiants de chaque consommateur sont stockés dans sops en tant que garage-<consumer>-key-id et garage-<consumer>-key-secret, importés dans Garage au premier démarrage.

Migration vers un cluster multi-nœuds

Nœud unique, replication_factor = 1. Pour évoluer vers un cluster multi-nœuds, augmenter replication_factor, exposer rpc_public_addr sur le maillage, et étendre garage-init pour piloter un layout multi-nœuds.

Initialisation du layout du cluster

En cas d’échec, attendre que le service garage soit pleinement opérationnel, puis le redémarrer.

  • enable bool Activer le service Garage S3 local
  • srvPort port Port de l’API S3 exposé sur l’IP interne
  • s3Region str Nom de la région S3 (doit correspondre à la config du consommateur)
  • capacity str Indication de capacité de stockage du nœud transmise à garage layout assign. Utilisée uniquement au premier démarrage pour l’initialisation du layout ; n’agit pas comme un quota strict sur le système de fichiers sous-jacent. Suffixes pris en charge : B, KB, MB, GB, TB, PB.

✨ darkone.service.harmonia

Section intitulée « ✨ darkone.service.harmonia »

Harmonia : serveur local de cache binaire Nix (sert le /nix/store de cet hôte).

Expose les chemins du store construits / réalisés localement sur HTTP simple (port 5000), signés avec la clé de cache binaire déployée sur tout le réseau. À activer par hôte depuis usr/config.yaml (services.harmonia), comme tout autre service DNF.

Comment harmonia fonctionne avec le proxy nix-cache

Harmonia est une source de paquets, servis directement aux clients sur le LAN (in-zone) ou le tailnet (quand il est marqué global). Le proxy nix-cache par zone est un sujet séparé : il met en cache le cache binaire public (cache.nixos.org), jamais harmonia.

Les substituters de chaque hôte de la zone locale deviennent, par ordre de priorité :

  • les instances harmonia de sa propre zone (priorité la plus haute, LAN), puis
  • toute harmonia marquée global (typiquement sur le HCS, via le tailnet), puis
  • le proxy nix-cache de la zone (cache public).

Cet ordre est figé côté client avec ?priority= sur chaque URL de substituter (voir nix-cache.nix), car la priority définie ci-dessous est identique sur chaque instance et Nix trie les substituters par priorité annoncée, pas par ordre de liste.

Un hôte qui exécute harmonia ne reçoit pas sa propre instance comme substituter : elle ne servirait que des chemins que son store local possède déjà.

Les harmonia non-globales des autres zones ne sont jamais utilisées. La signature d’harmonia est transmise telle quelle, donc chaque hôte fait confiance à la clé publique harmonia déployée (usr/secrets/harmonia.pub). Le transport est en HTTP simple sur le LAN / VPN de confiance : l’intégrité vient de la signature NAR, pas de TLS.

Provisionnement de la clé de signature

just configure-admin-host génère automatiquement la paire de clés déployée quand usr/secrets/harmonia.pub est absent : la clé publique est commitée et la clé privée est injectée dans le secret sops harmonia-secret-key.

Avertissement de démarrage bénin sur les permissions de la clé de signature

WARN harmonia_cache::tls: /run/credentials/harmonia.service/sign-key-0 has insecure permissions 0o440; recommend 0600 est un faux positif : systemd expose les fichiers LoadCredential en mode 0440 appartenant à root, avec une ACL qui n’accorde l’accès qu’à l’utilisateur du service (systemd/systemd#29435) ; harmonia vérifie naïvement les bits de chmod. Surveillez quand même l’amont : harmonia rejette déjà fermement les clés TLS lisibles par le groupe au démarrage ; si cette politique s’étend un jour aux clés de signature, cette unité cassera à la mise à jour.

  • enable bool Active un serveur de cache binaire Nix Harmonia local

✨ darkone.service.idm

Section intitulée « ✨ darkone.service.idm »

Service DNF Kanidm (gestionnaire d’identités).

Les secrets sont générés, pas saisis

just configure-admin-host crée chaque entrée lue par ce module : les mots de passe du compte de secours (kanidm-admin-password, kanidm-idm-admin-password), le couple auto-signé de l’écouteur HTTPS interne (kanidm-tls-chain / kanidm-tls-key, 10 ans, CN=127.0.0.1) et un oidc-secret-<client> par client OAuth2 provisionné.     • displayName str Human-readable name shown on the kanidm consent screen.
    • imageFile path Application icon. Re-uploaded on every kanidm-provision run.
    • redirectPaths listOf str OAuth2 redirect paths (one per accepted callback URL).
    • landingPath str Auto-connect entry point path on the service.
    • enableLegacyCrypto bool Allow legacy JWT signing algorithms (eg. RS256).
    • allowInsecureClientDisablePkce bool Disable PKCE on the client (only for clients that do not implement it).
    • preferShortUsername nullOr bool Use the short username (no domain) in the preferred_username claim.
    • extra attrs Extra attributes merged into the provisioned client (claimMaps, etc).

✨ darkone.service.loki

Section intitulée « ✨ darkone.service.loki »

Loki + Alloy, statistiques HTTP avec Grafana.

Note

Collecte centralisée des logs d’accès Caddy, consommés par Grafana via un datasource Loki provisionné et un tableau de bord dédié.

Double schéma aligné avec monitoring.nix :

  • enable : déploie le serveur Loki + le datasource Grafana sur le même hôte que le service monitoring (Grafana).
  • isClient : déploie Alloy sur chaque hôte exécutant Caddy. Les logs Caddy sont attendus en JSON dans /var/log/caddy/access-*.log (voir dnf/modules/system/services.nix).

Par défaut, enable suit darkone.service.monitoring.enable et isClient suit services.caddy.enable : la configuration est entièrement automatique une fois le monitoring et Caddy actifs.

Pas d’authentification, tailnet uniquement

Loki accepte les lectures et écritures de toute personne pouvant l’atteindre. Le port 3100 est donc ouvert uniquement sur tailscale0 ; auth_enabled est le commutateur multi-tenancy de Loki, pas une connexion, et reste false.

Débogage et nettoyage manuel

Symptômes les plus courants après une (dés)activation de Loki ou un changement de format de log Caddy :

1. « NO DATA » sur le tableau de bord Caddy malgré des requêtes entrantes. Vérifier la chaîne d’ingestion de bout en bout :

Une réponse vide sur /loki/api/v1/* alors que /ready répond 200 indique que le frontend annonce la mauvaise adresse (voir common.instance_addr) ; journalctl -u loki | grep frontend= l’affiche. Redémarrer Loki après correction.

2. alloy.service: mkdir data-alloy/remotecfg: permission denied. Propriété orpheline de /var/lib/alloy héritée d’un ancien DynamicUser. Le ExecStartPre du service la corrige normalement, mais si bloqué (ex. unité en start-limit-hit) :

3. Grafana refuse de démarrer : Datasource provisioning error: data source not found. Conflit d’UID en base SQLite après modification du provisionnement (typiquement passage d’un UID auto-généré à uid = "loki"). L’option deleteDatasources gère cela en théorie ; sinon nettoyage manuel :

4. Fichiers de log Caddy obsolètes (ancien nommage avec : ou schéma, par ex. access-http:__nextcloud.log). Inoffensifs mais encombrants dans la sortie de la queue Alloy. Nettoyage après migration :

  • enable bool Déploie le serveur Loki + le datasource Grafana (co-localisé avec Grafana).
  • isClient bool Déploie Alloy pour collecter les logs d’accès Caddy locaux.
  • retentionTime str Durée de rétention des logs dans Loki (30 jours par défaut).

✨ darkone.service.matrix

Section intitulée « ✨ darkone.service.matrix »

Serveur Matrix (synapse) DNF avec les ponts mautrix.

Les ponts (whatsapp, signal, telegram, messenger, discord) sont utilisables par tout compte local : chaque utilisateur lie son propre compte distant en discutant avec le bot du pont (@whatsappbot, @signalbot, … puis login) ; les sessions sont isolées par utilisateur. Le network.matrix.admin déclaré administre les ponts.

Le double puppeting utilise la méthode officielle appservice (https://docs.mau.fi/bridges/general/double-puppeting.html 🡕) : un jeton doublepuppet appservice partagé permet aux ponts d’envoyer les messages provenant du distant en tant que vrai compte matrix de l’utilisateur. Secrets sops requis : mautrix-doublepuppet-as-token et mautrix-doublepuppet-hs-token (openssl rand -hex 32 chacun).

Les jetons as/hs appservice de chaque pont sont fournis par sops plutôt qu’auto-générés : le fichier d’enregistrement devient une fonction pure des secrets, donc réinitialiser le répertoire d’état d’un pont n’invalide jamais l’enregistrement que synapse a chargé (ce qui autrement nécessiterait un wipe d’enregistrement + redémarrage de synapse et produirait des erreurs « as_token was not accepted »).

Fédération

Section intitulée « Fédération »

La fédération se configure via darkone.service.matrix.federation :

  • enable = false : bloque toute fédération (liste blanche de domaines vide).
  • enable = true; whitelist = [ ] : fédération ouverte avec tous les serveurs.
  • enable = true; whitelist = [ "ami.org" ] : liste blanche (entrante + sortante).

La découverte reste verrouillée dans tous les cas (salles absentes des annuaires distants, profils privés sur la fédération), donc le réseau est joignable mais pas recherchable.

Sans risque pour les enfants

Une fédération ouverte laisse n’importe quel serveur fédéré envoyer des MP ou inviter des utilisateurs locaux. Pour un réseau familial, remplissez whitelist avec uniquement les serveurs de confiance.

L’auto-inscription des proches (friendRegistration.enable) ouvre des comptes locaux protégés par jeton aux côtés des utilisateurs OIDC Kanidm. Sans MAS, la frappe d’un jeton passe par l’API admin de Synapse (un admin serveur est requis) ; avec MAS, frappez-le sur l’hôte avec sudo dnf-mas manage issue-user-registration-token.

Un seul espace de noms, identifiants permanents

Les proches et les utilisateurs déclarés tirent du même espace de noms localpart, et un identifiant matrix n’est jamais libéré (unique dans users de MAS, la désactivation le conserve). Déclarer un utilisateur dont le localpart a déjà été pris par un proche fait échouer leur première connexion SSO : on_conflict reste sur fail ci-dessous, puisque toute autre valeur remettrait le compte existant à quiconque enregistre un nom correspondant en amont. Procédure de fusion dans le guide admin (operate/matrix.mdx).

Authentification nouvelle génération (MAS)

Section intitulée « Authentification nouvelle génération (MAS) »

mas.enable délègue toute l’authentification au Matrix Authentication Service (requis par Element X, la connexion par QR code, le portail self-service /account). Kanidm reste la source d’identité : MAS devient le client OIDC à la place de synapse, et synapse se contente de demander à MAS d’inspecter les jetons. Servi sur le même vhost : MAS possède la racine + les points d’entrée d’auth compat, synapse conserve /_matrix/* et /_synapse/* ; la découverte client est automatique (synapse sert lui-même auth_metadata), donc pas de changement well-known.

Secrets sops requis, tous créés par just configure-admin-host : mas-encryption-secret, mas-synapse-secret et mas-rsa-private-key.

dnf-mas (racine) encapsule mas-cli pour l’administration côté hôte : jetons d’inscription, promote-admin, register-user, syn2mas. MAS tourne avec DynamicUser et lit ses secrets depuis les credentials systemd, qui n’existent pas en dehors de l’unité en cours ; le wrapper reconstitue un répertoire de credentials équivalent à partir des fichiers sops, ce qui fonctionne que le service soit en marche ou non (syn2mas nécessite qu’il soit arrêté).

Immuable une fois démarré

mas-encryption-secret et l’ULID du fournisseur Kanidm ne doivent jamais changer après le premier démarrage de MAS (données chiffrées de la BDD / liens de compte amont).

Migrer une instance existante

Activer mas.enable sur un homeserver en service nécessite la migration syn2mas (comptes, mots de passe, sessions, identifiants externes). Déployez d’abord, puis, avec les deux services arrêtés : sudo dnf-mas syn2mas check, ... migrate --dry-run, ... migrate. Les bridges n’ont pas besoin d’un réenregistrement : synapse force MSC4190 sur chaque appservice dès que l’auth est déléguée. Procédure dans .specs/matrix-authentication-service.md.

Pas d’enregistrement par secret partagé sous MAS

/_synapse/admin/v1/register de synapse (enregistrement par secret partagé) est désactivé en mode délégué, ce dont se sert just configure-alert-bot pour créer un compte bot manquant. Créez-le au préalable, ou avec sudo dnf-mas manage register-user.

  • enable bool Activer le service matrix (synapse)
  • federation.enable bool Autoriser la fédération serveur-à-serveur. Faux bloque toute la fédération.
  • federation.whitelist listOf str Vide = fédérer avec tous les serveurs ; non vide = uniquement ces domaines (entrant + sortant).

✨ darkone.service.nix-cache

Section intitulée « ✨ darkone.service.nix-cache »

Proxy de cache binaire Nix par zone (nginx proxy_cache).

Met en cache le cache Nix public (cache.nixos.org) sur la passerelle de la zone afin qu’un déploiement à l’échelle de la flotte tire chaque closure du WAN une seule fois, puis la sert sur le LAN à tous les autres hôtes. Les chemins construits localement sont servis directement par harmonia (voir harmonia.nix) ; ce proxy ne se place jamais devant harmonia.

Pourquoi nginx et pas un proxy de réécriture

Un point de terminaison de cache fait face à un amont exactement. Un narinfo et son nar sont deux requêtes distinctes et l’URL du nar ne dépend pas de l’amont, donc un proxy multi-amont doit réécrire les URL narinfo dans son propre espace de noms et les suivre dans une base de données (l’approche qu’adoptait l’ancien proxy ncps, et la source de ses HTTP 500 « invalid nar hash » récurrents). Avec un seul amont, il n’y a pas d’ambiguïté : nginx met en cache narinfo + nar verbatim, les signatures transitent intactes et les clients les vérifient. Pas de réécriture, pas de base de données, ce bug est impossible par construction.

Topologie

  • serveur : l’hôte passerelle qui liste nix-cache dans config.yaml (un par zone). Exécute nginx sur l’IP interne, port network.ports.nixCache.
  • clients : tous les hôtes de la zone locale. Leurs substituters deviennent les instances harmonia de la zone (directes, LAN/tailnet) plus ce proxy.
  • clients nomades (roaming = true) : hôtes itinérants déplacés entre les zones. Leurs substituters sont les noms neutres de zone (harmonia.dnf.internal, nix-cache.dnf.internal) que le DNS de chaque zone résout vers ses propres services de cache (voir service/dnsmasq.nix), afin que le cache suive le portable.
  • enable bool le proxy de cache binaire Nix par zone (nginx devant cache.nixos.org)
  • maxSize str Taille maximale du cache sur disque ; au-delà, nginx évince les entrées les moins récemment utilisées.
  • roaming bool Hôte nomade (portable déplacé entre zones) : remplacer les substituters épinglés à la zone par les noms neutres de zone que le DNS de chaque zone résout vers ses propres services de cache. En dehors de toute zone DNF, les noms répondent NXDOMAIN instantanément et Nix retombe sur cache.nixos.org.

✨ darkone.service.prometheus

Section intitulée « ✨ darkone.service.prometheus »

Serveur de supervision Prometheus avec escalade déclarative via Alertmanager.

Prometheus & Grafana

Service autonome de métriques + d’alerting, indépendant de Grafana :

  • Interroge chaque nœud de zone portant la feature monitoring-node:<zone>.
  • Alertmanager route par gravité : warning -> Matrix #warnings, critical -> Matrix #incidents + mail (relais Postfix local).
  • blackbox_exporter sonde l’atteignabilité de la passerelle / du tailnet / du DNS, ainsi que les passerelles des autres zones : Prometheus d’une zone réside sur sa propre passerelle, seuls les pairs peuvent donc signaler qu’un site entier a disparu.
  • Les classes de nœud (critical/non-critical/disabled) proviennent des features alert-* ou du profil d’hôte (voir dnf/lib/alerts.nix).

monitoring (Grafana) requiert un prometheus sur le même hôte (imposé par le require du générateur). L’interface web est exposée à https://prometheus.<zone>.<domain> derrière oauth2-proxy (groupe admins), ce qui corrige aussi les liens d’alerte renvoyant vers Prometheus.

  • enable bool Activer le serveur de métriques + d’alerting Prometheus

  • retentionTime str Durée de rétention des métriques Prometheus

  • alerting.enable bool Activer Alertmanager (activé par défaut une fois les salons Matrix d’alerte provisionnés)

  • alerting.matrix.enable bool Diffuser les alertes dans les salons Matrix via le bot matrix-alertmanager

  • alerting.matrix.userId str ID utilisateur Matrix du bot d’alerte (par défaut depuis network.matrix.bot)

  • alerting.matrix.warningsRoom str ID du salon Matrix pour les avertissements (par défaut depuis network.matrix.warningsRoom)

  • alerting.matrix.incidentsRoom str ID du salon Matrix pour les incidents (par défaut depuis network.matrix.incidentsRoom)

  • alerting.email.enable bool Envoyer aussi les alertes critiques par mail (via le relais Postfix local)

  • alerting.email.to str Destinataire des mails d’alerte critique

  • alerting.network.enable bool Sonder l’atteignabilité réseau (passerelle/tailnet/DNS) avec blackbox_exporter

  • alerting.network.internetProbeTargets listOf str Adresses IP externes que la passerelle de zone ping pour détecter une coupure WAN. Si toutes échouent, ZoneInternetDown se déclenche et inhibe les alertes de down (erronées) des hôtes accessibles uniquement via le WAN (par ex. le HCS). Liste vide = désactivé.

  • alerting.network.httpProbeUrls listOf str URLs HTTP(S) sondées pour la vivacité (ServiceEndpointDown) et l’expiration du certificat TLS (CertificateExpiringSoon/Critical). Vide par défaut : lister les endpoints web publics à surveiller. Les redirections vers un login SSO (3xx) sont comptées comme up ; l’expiration du certificat est lue depuis la poignée de main TLS quelle que soit la réponse HTTP.

  • alerting.silenceOnRebuild bool Émettre le flag dnf-maintenance (textfile collector) afin que les reconstructions inhibent les alertes d’un nœud

  • alerting.thresholds attrs Remplacer les seuils d’alerte de ressources (voir les valeurs par défaut dans dnf/lib/alerts.nix)

  • alerting.silences listOf submodule Alertes connues et acceptées qui ne doivent jamais notifier. Chaque entrée devient une route Alertmanager vers le récepteur null : l’alerte se déclenche toujours et reste visible dans les interfaces Prometheus/Alertmanager/Grafana, elle ne parvient simplement plus à Matrix ni par mail.

    Déclaré sur l’hôte qui fait tourner Prometheus, car c’est là que les règles et routes de la zone sont générées. Un module consommateur à l’échelle de la flotte (usr/modules/alerts.nix) est l’endroit pratique : il est importé partout et ne prend effet que là où Prometheus tourne.

    Dernier recours

    Corriger ou reconfigurer d’abord la condition sous-jacente. Un silence masque un vrai signal, donc reason est obligatoire et la liste reste auditable.

    • alert str Nom de l’alerte à mettre en sourdine (label alertname). Toujours restreint, afin que les niveaux de gravité voisins restent armés.
    • host nullOr str Restreindre le silence à un seul hôte. Null met en sourdine l’alerte pour toute la flotte.
    • matchers attrs Étiquettes de correspondance exacte supplémentaires, combinées en ET avec les autres (par ex. le point de montage ou le device visé par l’alerte).
    • reason str Pourquoi cette alerte est acceptée, et ce qui rendrait le silence supprimable.

✨ darkone.service.restic

Section intitulée « ✨ darkone.service.restic »

Module de sauvegarde Restic : serveur REST + cibles de sauvegarde par hôte.

Deux rôles, un module

  • Serveur : un hôte disposant de restic dans ses services config.yaml lance le serveur REST (enableServer) et stocke le dépôt de chaque hôte.
  • Client : tout hôte avec enable = true déclare des targets de sauvegarde (chemin local ou rest:http://restic.<zone>:<port>).

Deux mots de passe, ne pas les confondre

  • Phrase de passe du dépôt : restic-password-<zone>, chiffre le contenu du dépôt.
  • Identifiant REST : restic/<hostname>/rest-password par hôte, authentifie l’hôte auprès du serveur REST.

Les deux sont créés par just configure-admin-host (idempotent), qui lit les hôtes et zones déclarés dans la flotte.

Exemple (configuration machine) :

Structure du dépôt par cible : un dépôt par catégorie, nommé d’après celle-ci.

Le chemin du dépôt fait exactement deux niveaux de profondeur

Le serveur REST sert des dépôts à au maximum deux composantes sous son --path : <hostname>/medias répond, <hostname>/srv/medias renvoie 404 et restic affiche un message trompeur repository does not exist. Le sous-chemin est donc le nom nu de la catégorie, jamais le répertoire source. Une structure identique pour les cibles locales et REST permet de déplacer un dépôt de l’un vers l’autre sans renommage.

Un serveur REST inaccessible ignore l’exécution

Chaque cible rest: porte une sonde d’atteignabilité ExecCondition. Une sauvegarde dont le serveur est arrêtée est ignorée, jamais en échec : pas de SystemdUnitFailed nocturne, pas de quart d’heure de tentatives restic, et pas de initialize créant un dépôt vide contre un endpoint mort. La sauvegarde manquante apparaît néanmoins via ResticBackupStale / ResticBackupCritical, qui surveillent la dernière exécution réussie.

listenAll élargit la liaison, pas le pare-feu

Le serveur lie params.ip, c.-à-d. l’adresse LAN sur une passerelle. Les clients l’atteignant depuis une autre zone via le tailnet nécessitent listenAll = true (liaison sur 0.0.0.0). Le pare-feu reste la frontière : lan0 reçoit le port via getInternalInterfaceFwPath, tailscale0 est déjà une interface de confiance sur une passerelle, et le WAN ne l’ouvre jamais.

Migrer les dépôts créés avant cette structure

Les dépôts écrits lorsque le sous-chemin reflétait le répertoire source se trouvent sous <hostname>/srv/{nfs,medias}. Renommez-les sur le serveur avant la prochaine exécution : initialize = true créerait sinon un dépôt vide au nouveau chemin et lancerait silencieusement un re-semis complet.

  • enable bool Activer le client de sauvegarde restic
  • enableDryRun bool Mode simulation
  • enableWaitRemoteFs bool Lancer les sauvegardes uniquement après remote-fs.target
  • enableServer bool Activer le serveur REST restic
  • listenAll bool Lier le serveur REST sur 0.0.0.0 (clients hors site)
  • serverDataDir str Racine de stockage locale du serveur REST (dépôts de tous les hôtes)
  • targets listOf submodule Destinations de sauvegarde pour cet hôte (chemin local ou URL REST)
    • name str Identifiant de cible, utilisé dans les noms de sauvegarde/unités (<category>-<name>)
    • root str Racine du dépôt : chemin local ou URL REST
    • zone str Zone sélectionnant la phrase de passe du dépôt (restic-password-<zone>)
    • categories listOf ( enum [ "system" "nfs" "medias" ] ) Contenu à sauvegarder vers cette cible
  • nfsPaths listOf str Répertoires NFS (/srv/nfs/<xxx>) inclus dans la catégorie ‘nfs’
  • mediasPaths listOf str Répertoires Médias (/srv/medias/<xxx>) inclus dans la catégorie ‘medias’
