VPN (Headscale / Tailscale)

The VPN meshes the zones, the coordination server and remote devices : Headscale 🡕 coordinates from the HCS, Tailscale 🡕 is the client on each node. This page gathers the operational workflows. Routing, DNS, MagicDNS, access policy and keys are explained in Tailnet operation.

Enabling the VPN

Enabling coordination and declaring the HCS (profile: hcs) is enough :

The role of each node follows from the topology :

Gatewaytag:gw-<zone>subnet router : publishes its zone’s /16

Personal deviceits ownerservices, according to their groups

An admin machine is a host whose groups contains admin and whose host file enables the client :

autoPauseOnLan pauses the client when the laptop is plugged into a zone (NetworkManager required).

Enrolling a machine

Section titled “Enrolling a machine”

Machines join the tailnet without a shared key : the HCS creates a single-use key for each of them, with their declared tags. just configure handles this, and so does just full-install. The recipe alone can be re-run at any time :

It is idempotent :

SituationEffect
Node enrolled, name and tags conformnothing (already enrolled)
Different tags or namecorrected on the HCS, without reconnection
Never enrolled, deleted or reinstallednew key, registration
Older offline node with the same namedeleted, the new one takes the name
Older online node with the same namerefused : two machines carry this name
Host without Tailscale clientignored

The mechanism is detailed in Activation keys and enrollment.

Deploying the HCS after declaring the host

The HCS only creates a key for a host it knows. A host just added to etc/config.yaml first requires just apply hcs, otherwise : no declared tailnet identity.

Failure during an installation

HCS unreachable, just configure warns without stopping : re-run just tailnet-enroll <host> once the HCS is back.

New address after a reinstallation

Headscale assigns addresses in order and does not allow fixing them. A reinstalled machine receives a new tailnet address : for a gateway, report it in vpn.ipv4. To keep it, restore the client state rather than re-enrolling (see Migrating a gateway’s hardware).

Connecting a personal device

Section titled “Connecting a personal device”

A smartphone or a personal computer connects with the Kanidm identity of its owner : neither key, nor manual validation.

Can connectCondition in etc/config.yaml
Administratoradmin or nix-admin profile
Member of a zonezone-<zone> group

These accounts form the Kanidm group tailnet, provisioned on its own ; Kanidm refuses the others. To open access, add the group to the user, regenerate, then just apply hcs. The user then follows Connect a device.

The device belongs to the person (alice@) and expires after 180 days : they then reconnect with their identifier.

Connection page not found

Split DNS sends every domain.tld to the HCS through the tunnel, including headscale.domain.tld and idm.domain.tld. As long as the tunnel is not up, the browser cannot resolve them. Workaround : disable “Use Tailscale DNS” in the app while connecting, then enable it again.

Adjusting the access policy

Section titled “Adjusting the access policy”

The policy is generated from the topology : its rules are detailed in Access policy. Options adjust it, on the HCS :

Option darkone.service.headscale.DefaultEffect
policy.adminDevices{ }personal devices allowed in SSH : name → tailnet IPv4
policy.exitNodeSources[ ]sources allowed to exit to the Internet through the HCS
policy.extraHosts{ }extra aliases : name → CIDR
policy.extraAcls[ ]rules appended after the generated rules
policy.enforcetruefalse : everything allowed, for a migration only
nodeExpiry"180d"personal devices expiration (0 : never)

Then just apply hcs : the policy is checked at build time, and Headscale reloads it without restarting.

Address of a declared device

adminDevices targets an IPv4 address. A device re-registered as a new node changes address : HeadscaleNodeDrift reports it, report the new one.

Exit node

Opening exitNodeSources is not enough : the user selects the HCS as exit node in their application.

Administration

Section titled “Administration”

On the HCS (just enter hcs) :

CommandUsage
sudo headscale nodes listnodes, owner, tags, addresses, expiration
sudo headscale nodes list-routesadvertised and approved routes
sudo headscale nodes rename -i <id> <name>rename a node
sudo headscale nodes expire -i <id>force a reconnection
sudo headscale nodes delete -i <id>delete a node
sudo headscale users listowners of personal devices
sudo headscale preauthkeys listpre-authorized keys : tags, usage, expiration
sudo headscale policy getserved policy
sudo dnf-tailnet-enroll status <host>declared identity of a host

Tags and routes are not set by hand : just tailnet-enroll sets the declared tags, the policy approves the routes. The other client settings (advertised routes, Tailscale SSH off, exit node) are realigned by tailscaled-autoconnect, at startup and at deployments that modify it.

JSON outputs

nodes list -o json and preauthkeys list -o json may contain pre-authorized keys : do not copy them into a ticket or a chat room.

Audit and alerts

Section titled “Audit and alerts”

Every 15 minutes, headscale-audit compares the real nodes against the declared topology, without modifying anything. The details of the discrepancies are in its journal :

AlertReportsAfter
HeadscaleNodeDriftHCS or gateway missing, wrong tags, address different from the declared one30 min
HeadscaleUnexpectedNodetagged node not declared, or device from an account outside the tailnet groupimmediately
HeadscalePolicyInvalidpolicy refused, or served policy different from the file30 min
HeadscaleOidcFallbackKanidm missing at Headscale startup : OIDC connections cutimmediately
HeadscaleNodeExpiringpersonal device expiring within 7 days1 h
HeadscaleAuditStaleaudit without success for over an hourimmediately

All are in warning, on the Prometheus that supervises the HCS. A missing admin machine is not an anomaly ; if present, its tags are checked.

After HeadscaleOidcFallback

Kanidm is back, restart Headscale : sudo systemctl restart headscale.

Client self-repair

Section titled “Client self-repair”

A tailscaled can silently detach from Headscale : the control connection is lost while the service remains “active”, and a gateway’s subnet becomes unreachable. A local watchdog detects and fixes this case, on each Tailscale client.

AspectBehavior
Probeevery 60 s : tailscale status (backend, online status)
Debounce3 consecutive failed probes (~3 min) before acting
Fixrestarts tailscaled, which reconnects to the control plane
Anti-loopa single fix per 10 min window
Unenrolled nodeno restart (NeedsLogin) : just tailnet-enroll
Portable on pausewatchdog stopped, metric removed
Observabilitydnf_tailscale_healthy, dnf_tailscale_selfheal_restarts_total (textfile node_exporter)

Two alerts accompany the mechanism :

  • TailscaleUnhealthy : still detached after 10 min, despite the fix ;
  • TailscaleFlapping : more than 3 fixes in one hour.

Enabled by default

To disable it on a host : darkone.service.tailscale.selfHeal.enable = false;.

Control plane bootstrap

Section titled “Control plane bootstrap”

On a gateway, dnsmasq forwards any domain.tld to the HCS resolver through the tailnet : the client would need the VPN to find the server that brings up the VPN. At boot, moreover, the local resolver is not listening yet.

Each Tailscale client therefore receives the HCS public address in its /etc/hosts, derived from etc/config.yaml (the HCS itself is excluded). dnsmasq answers this name from that file, never forwarding it :

The client thus connects without any resolver, including when the local DNS is down, precisely when the self-repair must be able to act.

HCS address change

/etc/hosts takes precedence over DNS. If the VPS address changes, update etc/config.yaml then redeploy the Tailscale clients : as long as they carry the old entry, they do not reconnect, even with a correct public DNS.
