AI spaces

An AI space is a DNF host with the ai-space profile, usually a microVM guest. It runs an OpenClaw 🡕 assistant reserved for its members, with its own secrets and its own data.

In progress

Web access, SSO, Matrix channel, Claude Code, Codex, OpenCode, MCP and skills in place. Hermes comes in a future release.

Create a space

Section titled “Create a space”

  1. Declare the host and its members

    The host’s users are its members: DNF creates the Kanidm group space-<host> for them.

    monitoring-node places the space under the zone’s supervision: without it, neither a space failure nor the assistant stopping triggers an alert.

    The owner is the member whose subscription runs the assistant: they receive approval requests and spontaneous messages (reminders, scheduled tasks). As the only member, they are implicit. With several members, they are declared in usr/machines/ia-pro/configuration.nix (the order of users is not preserved):

  2. Initialize the space

    just space-init ia-pro: host key, secrets (see Isolated hosts) and, if the network has Matrix, the bot @ia-pro:<domain>. Then commit usr/secrets/ and var/generated/spaces/.

  3. Deploy

    The hypervisor, the zone gateway (vhost, DNS) and the HCS (Kanidm group): just apply hyperviseur,gw,hcs.

  4. Connect the AI provider

    Once per space, from the host (just enter ia-pro), for each owner subscription used for the space’s models (see Models and subscriptions):

    SubscriptionModelsLogin
    Claude Pro/Max, via the claude CLIanthropic/* (default: anthropic/claude-sonnet-5-5)sudo -u openclaw -H claude auth login
    ChatGPT Plus/Pro, via the codex pluginopenai/*openclaw models auth login --provider openai

    The host’s openclaw command switches to the service user by itself, even from the owner’s account (see Access). openclaw models status checks the connection, which stays in /var/lib/openclaw, persistent.

Why an openclaw user

The assistant reads untrusted content (web, messages, documents): a dedicated system user keeps it away from members’ accounts, their keys and their connections. Members have no sudo, except for the openclaw CLI (see Access): administration goes through the nix account.

Update

A space created before the assistant’s local password must go through just space-init <host> again before deployment: it generates the openclaw-gateway-password secret, with which the host’s openclaw command reaches the service.

Models and subscriptions

Section titled “Models and subscriptions”

A model goes through the owner’s subscription when its provider appears in subscriptions, otherwise through an API key.

OptionRole
modelMain model, <fournisseur>/<modèle>
extraModelsOther models, chosen in the conversation with /model
subscriptionsOwner subscriptions : anthropic, openai
apiKeysAPI keys, by variable name
providersProviders not in OpenClaw, OpenAI-compatible

Each key (apiKeys, providers.<nom>.apiKey) is stored before deployment in the space’s secrets, under openclaw/<VARIABLE> (just space-sops <hôte>).

Anthropic key and Claude subscription

The claude CLI prefers ANTHROPIC_API_KEY over its sign-in : alongside the anthropic subscription, DNF does not pass this key. To pay for Claude per use, remove anthropic from subscriptions.

Section titled “OpenAI-compatible provider”

A provider not in OpenClaw, such as Nous Portal, is declared with its address, key and models :

A personal subscription (ChatGPT, Claude) shared by several members falls outside the terms of use : a team space takes a team plan or API keys (subscriptions = [ ]).

Matrix

Section titled “Matrix”

Members write to the bot @<hôte>:<domaine> in direct message, end-to-end encrypted. The channel only exists if the network declares the matrix service: without it, the space runs on its web interface alone.

ElementRule
Who is listened toThe space’s members (@<login>:<domaine>), DM only; other accounts are ignored
RoomsIgnored: non-members would read the replies there
SessionsOne per member when there are several, otherwise a single one for all channels
Command validationNone by default (see Security); any request goes to the owner, via DM
Unsolicited messagesSent to the owner, via DM
Encryption keysIn /var/lib/openclaw, persistent

Device verification

On first startup, the bot asks for its session to be verified (openclaw matrix verify status on the host). Until it is verified, Element flags its messages as unverified.

Voice conversation

Section titled “Voice conversation”

The microphone button in the web interface opens a voice conversation, interruptible, on desktop and phone alike. OpenAI’s real-time voice (GPT-Live) answers ; the space’s assistant does the work (tools, files, MCP), whatever its model.

OptionDefaultRole
talk.modelgpt-live-1-codexChatGPT subscription, otherwise OPENAI_API_KEY
talk.voicecoveAlso arbor, breeze, ember, juniper, maple, sol, spruce, vale
talk.instructionsnoneAdded instructions (language, tone)

The owner’s ChatGPT sign-in is required (openclaw models auth login --provider openai), even with an assistant on Claude, or an OPENAI_API_KEY key (see Models and subscriptions). At most eight conversations at a time, 30 minutes each.

To be validated

Not yet tried in a browser or on a phone.

Agent tools

Section titled “Agent tools”

MCP servers, skills and tools are declared once per space, in usr/machines/<hôte>/configuration.nix. The assistant and each member (Claude Code, Codex, OpenCode) receive the same ones.

OptionRole
darkone.host.ai-space.mcpMCP servers, local (command, args, env, secretEnv) or remote (url, headers)
darkone.host.ai-space.skillsSkills by name : SKILL.md content, file or directory
darkone.host.ai-space.packagesTools in the assistant’s and members’ PATH
darkone.host.ai-space.enableClaude, enableCodex, enableOpenCodeClaude Code, Codex and OpenCode, enabled by default
darkone.host.ai-space.projectsDirShared projects directory (default /var/lib/projects)
darkone.service.openclaw.execCommand policy (see Security)
darkone.service.openclaw.identityAssistant name, emoji and avatar (name, emoji, avatar)
darkone.service.openclaw.workspaceAssistant workspace files (AGENTS.md, SOUL.md…)
darkone.service.openclaw.projectsGit repositories cloned once into the projects directory
darkone.service.openclaw.transcriptionVoice note transcription (see Transcription)

MCP secrets : secretEnv only

env and headers are written to the Nix store, readable by everyone. An API key goes through secretEnv, for a local server : each variable is read from the space’s secrets file, under the mcp/<serveur>/<VARIABLE> key (just space-sops <hôte>, before deployment). A remote server receives no secret.

Workspace

Declared files are rewritten each time the assistant starts. The others (memory, files created by the agent) belong to it. Projects are never updated automatically ; a failed clone is reported in journalctl -u openclaw-projects without blocking deployment. An SSH repository uses the openclaw user’s key, to be created once (sudo -u openclaw -H ssh-keygen -t ed25519) then declared on the forge (/var/lib/openclaw/.ssh/id_ed25519.pub) ; the server key is accepted on the first clone.

Transcription

Section titled “Transcription”

Voice notes, from Matrix or the web, are transcribed by whisper.cpp, with no external service :

SpaceTranscription
MicroVM guestHypervisor server, large-v3-turbo model
Physical machineOn the space, small model (466 Mo, CPU)

Hypervisor server unreachable or too slow : the space transcribes by itself with small. transcription.backend = "local" always keeps transcription in the guest. The language is detected for each note ; transcription.language = "fr" fixes it.

Projects and coding agents

Section titled “Projects and coding agents”

The projects directory (/var/lib/projects, linked as ~/projects for each member) is shared : any file created by a member or by the assistant remains editable by the others. It is the assistant’s working directory ; its instructions and memory stay in its workspace.

From the conversation (web or Matrix), the assistant hands code to Claude Code, Codex or OpenCode :

ModeUse
/acp spawn claude (or codex, opencode)Coding session tied to the conversation, can be resumed
Background task (coding-agent skill)Long work, completion reported by message

Each tool signs in once, on the host :

ToolSign-in
Claude CodeThe owner’s (see Create a space)
Codex (session)sudo -u openclaw -H codex login --device-auth
Codex (background task)sudo -u openclaw -H env CODEX_HOME=/var/lib/openclaw/.codex-coding-agent codex login --device-auth
OpenCodesudo -u openclaw -H opencode auth login

Update

projects used to be cloned into /var/lib/openclaw/workspace/projects/. They are now cloned into the projects directory : move existing clones there, or let them re-clone at the next start.

Workflows

Section titled “Workflows”
ToolUse
AutomationsAssistant scheduled tasks (morning briefing, monitoring)
Lobster 🡕Chaining steps with approvals, resume without redoing everything

The assistant and the interface create their own automations ; Nix can also declare some :

OptionRole
schedule, messageWhen, and the request made to the assistant
announceSends the answer into the conversation (default)
modelModel specific to this task
enablefalse : disabled, then re-enableable from the interface only

Declared automations are resynchronized on each start : a change made in the interface is overwritten, a removed declaration deletes its task. The others are never touched.

Lobster is enabled with lobster = true ; its files go through the workspace (workspace."workflows/tri.lobster" = ./tri.lobster;), and the assistant runs them on demand.

Lobster has not been tried on a space yet.

Member accounts

Section titled “Member accounts”

Each member has a Linux account on the space, lightweight:

ItemOn the space
Home Manager profilespace-member (zsh, git, vim, tmux), instead of their own
Space toolsClaude Code, Codex and OpenCode, with the space’s MCP and skills (darkone.home.aiSpace)
Customizationsusr/users/<login>/space.nix (all their spaces), then usr/users/<login>/spaces/<host>.nix (this space), if they exist
usr/users/<login>/default.nixIgnored: reserved for their workstations
Rightsprojects group, no sudo except for the openclaw CLI, whatever their profile

Administration of the space goes through the nix account (just enter <host>).

Customize a space

These files are ordinary Home Manager modules: packages, aliases, git configuration, other imported modules. A personal MCP is added there via programs.mcp.servers.<name>.

Each member connects their own subscriptions, once: claude (then /login), codex login --device-auth and opencode auth login. OpenCode accepts a ChatGPT subscription or an API key, not the Claude subscription.

Access

Section titled “Access”
ItemRule
Addresshttps://openclaw.<zone>.<domain>
LoginKanidm SSO, restricted to the space-<host> group
DevicePaired on first visit, without administration or approval rights (owner only, see Editable configuration)
Administrationopenclaw CLI on the host
Assistant portReachable from the zone gateway only

Alone, openclaw opens the assistant’s terminal (like openclaw tui). It runs under the service user, for the nix account and, through a sudo rule, for darkone.service.openclaw.cliUsers (default: the owner). Other members go through the web interface.

The CLI is worth the openclaw account

Subscription logins, administration rights, terminal ! commands: only add to cliUsers members to whom the service can be entrusted. With sudo restricted to the wheel group (R38 hardening), cliUsers stays empty.

Modifiable configuration

Section titled “Modifiable configuration”

By default, Nix freezes the assistant’s configuration : the web interface displays it read-only. darkone.service.openclaw.mutableConfig = true makes it modifiable, in the interface or via openclaw config set on the host, and gives the owner administrative rights.

SettingsWho decides
Access, Matrix channel, plugins, MCP, transcriptionNix : restored at startup and on every change
Model, commands, identityNix on first startup, then the interface
OthersThe interface

Setting seeded by Nix

Once written, a model, command or identity setting no longer follows Nix. openclaw config unset <clé> removes it : Nix immediately rewrites it with its value.

Security

Section titled “Security”

By default, the assistant runs its commands without validation, like OpenClaw : the barrier is the space itself (microVM cut off from the LAN, secrets specific to the space). Its service is also confined : it only writes to /var/lib/openclaw and the projects folder, and sees neither the members’ personal folders nor their processes.

darkone.service.openclaw.exec selects the policy :

ValueCommands
full (default)All, without validation
askAllowlisted ones pass, the others are submitted to the owner
autoA model examines those outside the allowlist and submits doubtful cases to the owner
allowlistAllowlisted ones only
denyNone

The allowlist is filled on the host : openclaw approvals allowlist add --agent main <chemin>.

Validation and Claude Code

With an anthropic/* model (claude CLI), outside full, pipes, redirections and substitutions are refused without a prompt : the assistant becomes noticeably less capable. Validation prevents mistakes; it does not stop a hijacked assistant, which runs under the same user as the service.

Validation reserved for the owner

Only the owner validates, by DM or in the web interface. A device paired before this setting keeps its right : remove it with openclaw devices list then openclaw devices remove <id>, it re-pairs on the next visit.

What the assistant can read

It runs under the openclaw user : everything the service holds is within its reach, including the owner’s connection to the AI provider and the Matrix bot token. Trapped content (web page, document, message) can make it disclose this information : do not entrust anything to a space that must not be able to leak it.

Trusted members

A space is a single circle of trust : each member’s web interface displays all sessions, including the others’ DMs. People who do not trust each other each take their own space.
