Deployment and updates

The fleet is deployed with colmena 🡕: a single command builds and applies the configuration on one or more hosts, remotely, from the admin workstation.

Apply a configuration

Section titled “Apply a configuration”
  • target = hostname, pattern ('*'), list (a,b) or colmena tag (@server).
  • action = switch (default), boot, test or build.
CommandPurpose
just apply <target>Build + activate on the target(s)
just apply-localApply on the current machine (alias al)
just apply-verbose <target>Same as apply in trace mode (alias av)

Build on target

apply builds on the target host (--build-on-target): the admin workstation doesn’t need the power or architecture of the deployed machines.

Deploy safely

Section titled “Deploy safely”

Build confidence through action: each step is less risky than the next.

Progress from core to edge: deploy nodes in this order, to never cut off access to a node by the one preceding it.

Why this order

A remote host’s connectivity depends on its gateway, which depends on the VPN coordinated by the HCS. Deploying a link before its support can make subsequent hosts unreachable.

Updating

Section titled “Updating”

The system is locked down by flakes. Updating = refreshing the inputs, then redeploying.

Always test first

Before a wide rollout, validate locally: just check, then just apply <pilot-host> on a single test host.

Updating the fleet with fleet-update

Section titled “Updating the fleet with fleet-update”

fleet-update runs the whole update in a single command: flakes, building all hosts, publishing closures to the fleet, testing in waves (hosts the network depends on first), then the definitive activation of validated hosts.

The AI at work

The AI analyses, acts on services and fixes the code — see AI analysis, Repairing a service and Repairing through code.

Launch

Section titled “Launch”

The recipe picks the tool to run, in this order :

SituationTool run
Co-development (src/dnf-fleet-update/ present)The sources, with bun
Active darkone.admin.fleet-update moduleThe installed fleet-update command
Any other casenix run .#fleet-update, per the project’s flake.lock

Prerequisites

  • Clean git trees: project, and dnf/ in co-development.
  • var/deployments/ ignored by git: /var/* rule from the boilerplate.

How a run unfolds

Section titled “How a run unfolds”
  1. Update: nix flake update of the project then of dnf/ (co-development), just clean, one commit per repository.
  2. Selection: hosts, profiles and zones read from var/generated/, filtered by --on; current zone inferred from the local IP; one builder elected per host.
  3. Build: all selected hosts, reachable or not, each on its builder.
  4. Publish: the closure of each reachable host is brought into its store, outside waves, before any activation.
  5. Test: switch-to-configuration test, one wave per profile; the next wave starts when all its hosts are OK or set aside.
  6. Switch: all hosts validated in test, all at once, regardless of wave order.

Why publish before activating

Serving and activating are two distinct needs. Once each host is served, a wave depends only on ssh: a gateway that restarts its network no longer deprives anyone of their substituter.

The host pulls first (nix build --max-jobs 0, which substitutes without ever compiling locally), and is only pushed as a fallback. A pull that fails is the ordinary case: a very fresh path is not yet in any cache.

Three options shorten this flow:

OptionEffect
--build-onlyStops after the build; in interactive mode, offers to continue
--skip-testNo test: the switch happens wave by wave, right after the build
--skip-switchNo switch: the run stops on what the test left in place

Preload the fleet without activating anything

--skip-test --skip-switch builds and publishes, then stops: each host holds its closure (state ready) without having activated anything. A subsequent run, or a --resume, then activates without copying anything more. Handy for separating a large package download from a short intervention window.

--build-only is the other extreme: nothing leaves the deployment machine, the publication itself is skipped.

Why the switch is not wave-based

Waves protect an unproven configuration. Once the test passed on each host, there is nothing left to protect: the switch fires at once, at most --max-parallel hosts activated simultaneously. With --skip-test, nothing has been proven: the switch resumes the wave order.

Resume an interrupted run

--resume restarts from the last folder of var/deployments/: update skipped, waves and options of the original run, and the hosts that still had work (remaining, offline, failed, or only tested). Builds are reused if the revisions of the project and of dnf/ have not moved and the paths are still in the store; otherwise they are redone. Nothing to resume: exit code 2, no run.

Distributed build

Section titled “Distributed build”

The deployment machine must not be the bottleneck of the fleet. Each host is therefore built by the elected builder for it. The election is recomputed at each run from var/generated/, never declared: changing the deployment topology must not rebuild the fleet.

OrderBuilder keptCondition
1The host itselfauto-build feature declared on the host
2The harmonia host of its zoneThe zone has one
3The global harmonia hostOne exists in the fleet
4The deployment machineDefault

The rule fits in one sentence: a builder must be able to serve what it builds. Hence the choice of harmonia hosts, whose /nix/store is already the cache of their zone, with nothing to bootstrap. A gateway without harmonia does not fit: its paths are not in any substitute.

The result stays on the builder. Publication then brings it to the hosts of the zone, over LAN, through their usual substitute.

nixpkgs sources downloaded by the builder

Each system embeds the nixpkgs source (about 200 MiB), new at each update and absent from any cache. Before sending it the derivations, the tool therefore asks the builder to download itself, from GitHub, the sources locked in flake.lock that its builds need: they no longer go through the upstream link of the deployment machine. A builder that cannot reach github.com receives them pushed, as before, without failure.

When to declare auto-build

A host that builds itself no longer receives any closure. This is decisive for a host isolated behind a slow link that carries a large package absent from the public cache, and it is the answer for a host of another architecture.

The choice is made per host, never per zone: RAM and disk are properties of the machine. Counterpart to weigh: the closure of derivations, several hundred MiB, goes up to it at each run that moves nixpkgs. It is the report’s copy counters that settle the case, not intuition.

Automatic fallback

Builder unreachable, failing, or of an architecture incompatible with its target → the build falls back to the deployment machine. No host fails because of a delegation, and the report names the builder that actually built.

The --no-distributed-build option brings everything back to the center, whatever the election. It is a debugging escape hatch: the rule comes from the fleet, the exception from the command line.

A zone without harmonia is expensive

Without a zone cache, there is neither local builder nor common source: each host gets its closure pushed, one by one, from the deployment machine. The report lists these zones and the number of pushed bytes shows it. Declare a harmonia on a host of the zone.

Wave order and critical hosts

Section titled “Wave order and critical hosts”

The fleet’s default values are declared in config.yaml :

KeyRole
deploymentOrderOne test wave per host profile, in that order
criticalProfilesProfiles whose failures also go to the incident room

Profiles separated by :, [others] designates the unlisted profiles. Optional block : without it, the tool applies the values above. The --deployment-order and --critical-profiles options take precedence over config.yaml.

Errors, diagnostics and repair

Section titled “Errors, diagnostics and repair”

A common error should be readable without knowing Nix. The tool keeps a signature table: a recognized pattern in a command’s output gives a plain-language message and the action to take.

Recognized patternWhat it meansAction
mismatch in field 'narHash'nix-eval-jobs isn’t bound to the same Nix as the systemStop
lacks a signature by a trusted keyThe deployment account isn’t a trusted user on this hostStop

The message is shown as the run progresses (hint:), once only, and is also found in the report’s Known errors section. It is added to the host’s reason, it never replaces it: the full trace stays in logs/.

Table actionWhat the tool does
RetryReplays the command, at most three times, if it is replayable: evaluation, build, derivation copy, pull
ExcludeContinues without the host; if already activated, first brings it back to its origin
StopStops the run, without asking any question

No signature calls for a retry today: the two known entries are stops.

A table action is not discussed

It also applies in interactive mode: a deterministic repair comes before the question. A nightly run and a supervised run therefore handle the same error the same way. The known error decides: stop line says it as the run progresses, and the host’s reason stays in the report.

Activation, profile installation, commit, and unit restart are never replayed on their own: only commands that can be re-executed without consequence are.

Deterministic collection. A host that fails while remaining reachable is interrogated before any decision: systemctl status, list of failing units, then each one’s log since the start of its wave.

What is collectedWhere it goes
Full output of commands and logslogs/<hôte>.diag in the run folder
Failing units, error extractReport’s Diagnostics section, incident message

Unit restart. An activation that ends with failing units leaves the host in error state. The tool then attempts a simple repair.

  1. Ten-second wait: a unit that is slow to start isn’t a failing unit.
  2. systemctl restart of all the failing units, in a single command.
  3. Re-reading the failing-unit list: it is what concludes, not the exit code.

Everything comes back up → the host resumes its course, rejoins the switch with the others, and the report notes a probable activation-order issue (Notes section). A unit resists → the host stays in error, its name and the unit’s are in the report.

What the interface shows meanwhile

The host carries a blinking label to the right of its name, with its activity indicator: under repair in yellow during deterministic repair, AI analysis and AI repair in magenta when the AI takes over.

AI analysis

Section titled “AI analysis”

The AI explains a failure : it reads the run state, the logs and, if needed, the code, then produces a plain-language analysis. With --ai-error-action repair it can then act on the failed units, and nothing else (see Repair a service). The run never waits for it — an analysis that fails, exceeds its timeout or its budget leaves the host exactly where it was.

Two options control it, both set to none by default : nothing goes to an AI until asked. A third one chooses the tool.

OptionDefaultRole
--ai-analysis none|passive|activenoneAnalysis depth, and end-of-run summary to the report
--ai-error-action none|analysis|repairnoneWhat the AI does when a host fails
--ai-model <tool>[:<model>][@<effort>]claude:opus@highTool and model, for example opencode:ollama/qwen3:32b
--ai-context <text>noneInstruction or context added to all AI prompts

For example, --ai-context "Répondre en français et rester concis." guides the style of the replies. On resume, the context of the initial run is carried over; an explicit --ai-context replaces it.

The fleet’s default model is set in config.yaml, the option takes precedence :

AI tools are not a dependency of the tool. claude and opencode are looked up in the PATH ; the module’s aiPackages option puts them there for the daily run. Missing or refused → a warning along the run, a note in the report, and the rest proceeds without AI.

What the AI is allowed to do

Section titled “What the AI is allowed to do”

The AI has neither shell nor free SSH. It only acts through the fleet-update tools, and the requested level sets the list presented to it: what it does not see there, it cannot ask for.

LevelTools presented
passiveRun state, host diagnosis, build and activation logs
active, analysis+ code reading (project and dnf/), host units and logs, read-only
repair+ one action on a host’s failed units, and editing the code that describes them

The retained level is the highest of the two options: --ai-analysis passive --ai-error-action analysis gives active. The built-in tools of claude and opencode are cut off, and the instructions those tools would pick up in the project (CLAUDE.md, user settings) are neutralized: the AI only sees what is shown to it.

Guard-railEffect
Read pathConfined to the project and dnf/, after link resolution; usr/secrets/ and .trash/ refused
Host, unitChecked against the run table before any command
Excerpts200 lines of log, 400 lines of source, truncated from the end: the error is at the bottom
Time, budget300 seconds per analysis; dollar budget for claude

Every tool call leaves a trace — one line along the run (AI reads usr/modules/nginx.nix) and one line in logs/ai.log of the run folder. A call refused by a guard-rail is traced too, with its reason.

When it intervenes

Section titled “When it intervenes”
  1. A host fails, with --ai-error-action ≠ none: after the deterministic collection and unit restart, before the question that decides its fate. The host carries AI analysis in magenta during this time, then returns to its state.
  2. A host recovers after a unit restart, with --ai-analysis ≠ none: the analysis explains the activation order, without touching the host’s state.
  3. End of run, with --ai-analysis ≠ none: a summary of the whole, written before the report that carries it.
  4. Pressing a, at any time: a free-form question. It receives an answer even under --ai-analysis none — without any tool: none removes the tools and automatic analysis, not the conversation.

Repairing a service

Section titled “Repairing a service”

--ai-error-action repair opens a second session on the host, right after the analysis and in the AI repair state. The first of its tools acts on services: systemctl start, stop, restart or reset-failed on the units the run saw fail. This is the gesture to prefer: it is local and reversible. When it is not enough, the AI fixes the code (Repairing through code).

  1. The grouped deterministic restart failed: the host stays in error.
  2. The AI analyses, in the AI analysis state, read-only.
  3. The AI repairs, in the AI repair state: it acts, then re-reads the failed units.
  4. Nothing failing anymore → the host resumes its course and joins the switch. Otherwise → the usual question, revert / keep / stop / rollback.
Guard-railEffect
UnitsOnly those the collection saw failing on this host; any other is refused
HostRefused if it is not currently being repaired: a read session never acts
AttemptsThree actions per host, refusals not counted; the fourth is refused
Stopping mid-runA run that stops repairs nothing: it is a new operation
ConfirmationIn interactive mode, a button question before each action: apply or skip

In non-interactive mode (night timer, --no-ui), the action passes without asking. It is strictly less risky than what the run already does without witness: the deterministic repair restarts all the host’s failed units.

Each action is counted, not just traced: it ends up in state.json and in the AI repair section of the report, refusals included, with its reason. A repaired host also carries a note in the report.

Repairing through code

Section titled “Repairing through code”

When no restart can help, the AI writes the fix in the project, validates it, commits it, and the sole host is then rebuilt and redeployed.

  1. edit_code rewrites a whole file. The git tree must be clean before the first edit, and the diff goes into logs/ai.log.
  2. validate runs the project cleanup, then re-evaluates and rebuilds this host alone.
  3. commit writes fix(<host>): <subject> — dnf/ first in co-development, then the project with its realigned lock.
  4. The host returns to built with its new path; its wave serves it once more: copy, activation, conclusion.
Guard-railEffect
PathsThe project, and dnf/ in co-development; never usr/secrets/, .trash/, .git/, var/generated/, etc/config.yaml nor a *.lock
Outside co-developmentdnf/ is a store path: writing it is refused, and would have changed nothing
TreeDirty before the first edit → refused: a repair commit only carries the fix
AttemptsOne attempt is a change. Validating and committing cost none, otherwise fixing would cost three times more than restarting
HooksNever bypassed: the commit goes through the repository gate like any other

The fleet ends up straddling two revisions

Only the repaired host is rebuilt: all the others keep the path the run had built at the start and switch with it. Until the next run, the fleet therefore runs on two revisions. The report and the alert message say it in plain words: Repaired in flight: <host>.

Consequence on resume: after a repair commit, --resume rebuilds everything. That is the guarantee itself — one does not redeploy paths built before the fix.

In non-interactive mode too

Under the night timer, the AI edits, commits and redeploys without asking. An unreviewed commit can therefore land on the branch. What makes it bearable: the required clean tree, the confined paths, the logged diff, the three attempts, and the automatic rollback that stays armed. If that is not what you want, leave --ai-error-action at none or at analysis in timer.extraArgs.

What AI repair is not

It is neither the deterministic repair (grouped restart, once, without AI), nor the retrying of a command decided by the signature table, nor a decision — excluding or stopping comes first, without a question. The AI only arrives after what is deterministic.

The analysis adds, it replaces nothing

A host’s raw reason, its failed units and the whole logs/ trace remain what they were. The analysis completes them, like the plain-language message of a known error.

Report and Matrix alerts

Section titled “Report and Matrix alerts”

Each run writes its folder in var/deployments/<date>-<mode>/: report.md (the report), state.json (the state --resume picks up), events.jsonl and the per-host logs. The path is shown at the end of the run.

The report details what the run actually did:

SectionWhat it gives
Steps, WavesDuration of each step, composition and duration of each wave
BuildersWho built what, fallbacks included
CopiesPer host: paths pulled and by which substituter, paths pushed, volume
Zones without a cacheRun zones that no harmonia serves
Hosts not deployedHosts left aside, and the reason
DiagnosticsPer failed host: failed units, then an excerpt of the error
NotesWhat the run observed: probable activation order after a unit restart
AI analysisAI analysis: one entry per analysed host, then the run summary
AI repairAI actions: host, action, outcome, and the reason for a refusal. A repair commit also appears in the header, Repaired in flight
Known errorsKnown traps from the signature table, in plain language

Reading the copy counters

A host pulling most of its content from harmonia <zone> proves that its zone’s cache plays its role. A host that gets a lot of volume pushed to it is on the contrary a candidate for a harmonia in its zone, or for auto-build. No copy line for a host → it already held everything, nothing travelled.

The --send-report option sends this report to the rooms of the alerts bot, installed beforehand via just configure-alert-bot.

SituationRoomContent
Run finishedwarningsSummary: hosts by state, duration, known errors
Critical hosts not deployedincidentsSeparate message: affected hosts, reasons and failed units
Stop on errorincidentsError that stopped the run, then summary

A host is critical when its profile appears in criticalProfiles. After a stop, the hosts left in test complete the incident message: a restart would bring them back to their previous generation.

Only the end-of-run summary reaches the message, never the per-host analyses, and it is capped there at six lines: beyond that, the message points to report.md. An alerts room is not a report.

The message repeats the report header, the exit code in the title:

Send impossible

The run remains valid and the report is written, but the command exits with 3. Under the timer, the unit fails, therefore the SystemdUnitFailed alert.

What sending requires

Sending goes through the just send-msg recipe: rooms and token remain the framework’s concern, the tool only writes the text. Nothing goes out if the bot is not provisioned, nor on an abort (^C, service stop).

Daily execution

Section titled “Daily execution”

On the deployment host, the module installs the tool and, with timer.enable, runs fleet-update --no-ui every day :

OptionDefaultRole
usernoneProject owner: git, age key, AI, Matrix
workDir/etc/nixosConsumer project on disk
aiContextnullContext added to the timer’s AI prompts; timer.extraArgs can override it
timer.onCalendar*-*-* 04:00Start time
timer.extraArgs[ ]Options added to --no-ui, --send-report for example
timer.timeout6hMaximum duration of a run

Exit codes and alerts

A run already in progress (code 4) is not an error. Any other failure, or exceeding timer.timeout, puts the unit in failure and triggers the alert SystemdUnitFailed.

Account and deployment host

The timer requires darkone.admin.nix on the host, and a user account with passwordless sudo.

Daily report

--send-report will become the default of timer.extraArgs when the packaged version of the tool knows how to send it. Add it until then, after verifying the sending manually.

Binary cache

Section titled “Binary cache”

Two services combine to avoid recompiling or re-downloading the derivations at each deployment.

ServiceRole
harmoniaServes the local, signed /nix/store directly to the hosts (LAN, or VPN if it is global).
nix-cachePer-zone nginx proxy that caches the public cache.nixos.org cache on the gateway.

A harmonia host has a second role: it is the elected builder of its zone, because it can serve what it builds.

A host queries these sources in the following priority order. The first fetch from the Internet is thus shared across the whole zone.

PrioritySourceScope
20zone harmoniaLAN, what the zone compiled
35zone nix-cache proxyLAN, shared mirror of the public cache
40cache.nixos.org directlysafety net if the gateway is down
45global harmonialast resort, over the VPN

How the order is guaranteed

Nix does not follow the order of the substituters list, it sorts the caches according to the priority each announces in its nix-cache-info. Yet these announced values are tied: all harmonia declare 30, and the proxy relaying cache.nixos.org as-is declares 40, like the direct access to the public cache. DNF therefore fixes the priority in the substituter URL (?priority=35), which overrides the announced value and makes the order in the table explicit.

Two intended consequences. The zone proxy sits ahead of the direct access to the public cache, otherwise zone sharing would never happen. And a global harmonia sits behind this public cache: harmonia serves a whole /nix/store, without being able to tell what it compiled from the rest, so a well-stocked host would capture all the traffic the public cache must serve. As a last resort, it is only consulted for what cache.nixos.org does not have, that is, its own builds.

A host does not use its own harmonia

This service serves its own /nix/store, so it can only provide paths already present locally. On this host, everything missing necessarily comes from another source: that is normal, its harmonia only benefits the other machines of the zone.

Nomadic host (multi-zone portable)

A laptop that changes zone must not keep substituters fixed on its declared zone: unreachable elsewhere, they cost timeouts on every request. Enable the roaming mode :

Its substituters become neutral names (harmonia.dnf.internal, nix-cache.dnf.internal) that the DNS of each zone resolves to its own caches → the cache follows the machine. Outside any zone, an immediate NXDOMAIN response → direct fallback on cache.nixos.org, without delay. Signature keys being common to the whole network, nothing else to configure.

Activation

harmonia and nix-cache are services to enable on a network host (nix-cache on the zone gateway). The harmonia signature key is managed by sops (just configure-admin-host).

Why a single-upstream proxy

nix-cache only relays one upstream (cache.nixos.org) : it caches narinfo and nar as-is, signatures intact. No URL rewriting nor database, therefore no HTTP 500 “invalid nar hash” error like the old ncps relay.

Build farm

Section titled “Build farm”

Fetching a package and building it are two distinct needs. The binary cache above covers the first. For the second, a powerful host of the network can take on the long compilations of an administrative host.

Declare it with the build-farm feature:

Each administrative host then adds it to its nix.buildMachines, joined over SSH by the deployment account nix. Nothing else to configure: the key and the authorization are already in place across the whole fleet.

Only long compilations go away

The delegation is deliberately narrow: the farm is only offered derivations declaring requiredSystemFeatures = [ "big-parallel" ], i.e. the kernel, browsers, llvm, rustc… Everything else is built locally. This is decisive when the farm is behind a slow link, since only the requested result makes the return trip.

Adjust with darkone.admin.nix.remoteBuilders: maxJobs, speedFactor, and mandatoryFeatures (empty list = everything goes to the farm).

build-farm or auto-build?

Two distinct mechanisms, combinable on the same host.

FeatureWho uses itWhat it moves
build-farmNix, on administrative hostsOnly the big-parallel derivations, whatever tool is launched
auto-buildfleet-update, at fleet buildThe whole system closure of the host that declares it

build-farm relieves an admin machine of its long compilations. auto-build removes a transfer to a host. They do not replace each other.

A farm is not a priority cache

Do not promote a remote farm to a priority global harmonia to share its results: harmonia serves the whole /nix/store and would capture the traffic the public cache must serve, across the slowest link of the network. That is the role of level 45 of the table above: last resort, never primary source.

Fallback if the farm is unreachable

The administrative host keeps big-parallel in its own system-features. When the farm does not answer, Nix simply resumes the compilation locally instead of failing. Do not remove this feature to force delegation.
